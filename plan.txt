# RepoMind – Full Project Walkthrough (28 Phases)

## Phase 1: Project scaffolding & environment

**Concept:** Set up the Python project with a clean structure, dependency management, and Dockerised PostgreSQL+pgvector.

**Why:** Every solid project starts with a reproducible environment. We want `docker compose up` to give us a ready-to-go database.

**Project files we create:**
```
repomind/
├── backend/
│   ├── app/
│   │   ├── __init__.py
│   │   ├── main.py                # FastAPI app entry point
│   │   ├── config.py              # settings
│   │   ├── database.py            # SQLAlchemy engine & session
│   │   └── models/                # SQLAlchemy models (empty for now)
│   ├── alembic/                   # migrations (initialised)
│   ├── requirements.txt
│   └── Dockerfile
├── docker-compose.yml
└── .env
```

**Step-by-step:**
1. Create the repo and virtual environment.
2. Install `fastapi`, `uvicorn`, `sqlalchemy`, `psycopg2-binary`, `pgvector`, `alembic`, `pydantic-settings`, `python-dotenv`.
3. Write `config.py` to read DB URL from environment.
4. Write `database.py` with async SQLAlchemy engine (or sync, we'll use async for better performance later).
5. Write `docker-compose.yml` with a `db` service using `pgvector/pgvector:pg16` image.
6. Run `alembic init alembic` and point it at our DB.
7. Create an initial migration just to test the connection.
8. Write a tiny FastAPI app with a `/health` endpoint that pings the DB.
9. Test with `docker compose up` and `curl localhost:8000/health`.

**Internal workings:** Docker Compose starts a Postgres container with the pgvector extension already enabled. FastAPI connects via `DATABASE_URL` in `.env`. Alembic will manage schema changes.

**Common errors:**
- Forgetting to install `psycopg2-binary` (or not matching architecture).
- `pgvector` extension not created – we’ll handle that in migrations.

**What we achieved:** A running backend with a database and a health check. The foundation is set.

```python
@router.post("/repositories")
async def ingest_repository(
```

**Files:**

## Phase 4: File filtering & reading

**Concept:** Walk the cloned repo, ignore irrelevant directories (`.git`, `node_modules`, etc.), and collect a list of allowed files with their content.

**Why:** Not every file is code; we only care about source files and documentation.

**Implementation:**
- Define allowed extensions: `.py`, `.js`, `.ts`, `.java`, `.md`, etc.
- Walk the directory tree with `pathlib`.
- Read each file’s text content.
- Store each file as a row in `code_files` with path, language (inferred from extension), and content.

**Background task:** After cloning, call `process_files(repo_version_id)` which inserts files.

**Testing:** Clone a tiny test repo (maybe a mock) and assert the right files are stored.

**Achievement:** The raw code is now in the database, ready for chunking.

## Phase 5: AST-aware code chunking (Python first)

**Concept:** Instead of splitting by character count, parse the code into logical units (classes, functions, imports) using Python’s `ast` module. For non‑Python files, fall back to a sensible line-based splitter.

**Why:** Chunks that map to real code symbols produce far better retrieval and allow precise line‑number citations.

**Implementation details:**
- For each Python file, use `ast.parse()` and a `NodeVisitor` to extract top‑level definitions.
- For each function/class, record `start_line`, `end_line`, and symbol name.
- Fallback: split the file at blank lines or into 50‑line windows with overlap.
- Create `code_chunks` rows with `file_id`, `start_line`, `end_line`, `symbol`, `content`, `language`.
- Store the raw chunk text.

**Testing:** Parse a known Python file, assert chunks are created and they match expected boundaries.

**Common errors:**  
- Indentation errors in the source – we must handle them gracefully (fall back to line splitting).
- Huge files: add a max‑chunk‑size limit.

**Achievement:** Every piece of code is now stored as a meaningful chunk that we can vectorise.

## Phase 6: Embedding generation & swappable provider layer

**Concept:** Define an abstract embedding provider interface, implement a local `sentence-transformers` provider (free), and generate embeddings for all code chunks.

**Why:** You want to swap providers later without changing the vector DB schema. The local option keeps costs at zero.

**Interface:**
```python
class EmbeddingProvider(ABC):
    def embed(self, texts: list[str]) -> list[list[float]]:
        ...
```

**Implementations:**
- `SentenceTransformerEmbedding` – uses `all-MiniLM-L6-v2` (dim 384).
- `OpenAIEmbedding` – calls `text-embedding-ada-002` (dim 1536) – optional.

**Config:**  
`EMBEDDING_PROVIDER=local` in `.env`.  
Use a factory to instantiate the right provider.

**Generation:**
- Batch‑fetch chunks without embeddings.
- Generate embeddings in batches of 64 (to avoid OOM).
- Store vectors using `pgvector`’s `INSERT` with `embedding`.

**Database:** `embeddings` table or add an `embedding` column to `code_chunks` (simpler). I’d put it directly in `code_chunks` to avoid a join.

**Testing:** Embed a known text, verify dimension and that a similarity query returns the same chunk.

**Achievement:** The entire codebase is now searchable by meaning.

## Phase 7: Semantic search API

**Concept:** Accept a query string, embed it, and perform a cosine similarity search against the `code_chunks` table using pgvector.

**Why:** This is the core retrieval step for RAG.

**Endpoint:** `POST /search` with `{"query": "user authentication", "top_k": 10}`.

**Implementation:**
- Embed the query with the same provider.
- Use SQLAlchemy with `func.cosine_distance` or the `<=>` operator.
- Return a list of `CodeChunk` with file path, line numbers, symbol, and similarity score.

**SQL example:**
```sql
SELECT *, 1 - (embedding <=> query_vector) AS similarity
FROM code_chunks
ORDER BY embedding <=> query_vector
LIMIT 10;
```

**Testing:** Seed a few known chunks, query, and assert the most relevant appears first.

**Achievement:** We can retrieve relevant code snippets from a natural language question.

## Phase 8: RAG answer generation with citations

**Concept:** Feed the user’s question and the retrieved chunks to an LLM with strict instructions to only use provided context and to cite every claim with `[file:line]`.

**Why:** This is the core product – grounded answers that build trust.

**Implementation:**
- Build a prompt template:
  ```
  You are a codebase assistant. Answer using ONLY the context below.
  If unsure, say "I don't have enough evidence."
  Cite every technical claim like: [path/to/file.py:start-end]
  
  Context:
  {chunks}
  
  Question: {question}
  ```
- Call the LLM (DeepSeek via API, using the provider abstraction).
- Parse the response to extract citations (regex `\[([^\]]+):(\d+)-(\d+)\]`).
- Return the answer and a list of `Citation` objects with file path, lines, and the snippet text.

**Swappable LLM:** We’ll build the provider layer in Phase 9; for now, just hardcode DeepSeek.

**Testing:** Provide a chunk about login, ask “how does login work?”, assert the answer mentions the file and line.

**Achievement:** The system now answers code questions with evidence. That’s already an MVP.

**Interface:**
```python
class LLMProvider(ABC):
```

**Implementations:**

- `OpenAIProvider` – standard `openai.OpenAI()`.

**Config:** `LLM_PROVIDER=deepseek` in `.env`.

**Update Phase 8:** Use `get_llm_provider()` to get the current instance.

**Testing:** Mock the HTTP call, assert the right endpoint is hit.

**Achievement:** LLM is now a plug‑and‑play component.

## Phase 13: Hybrid search (keyword + semantic)

**Concept:** Combine a traditional keyword search (Postgres full‑text search) with vector similarity to improve retrieval, especially for exact symbol names.

**Why:** Semantic search alone may miss the exact function name `create_access_token` if the query phrase is different. A hybrid approach lifts retrieval metrics.

**Implementation:**
- Add a `tsvector` column to `code_chunks` that’s automatically updated.
- Use a query like:
  ```sql
  SELECT ..., (0.7 * vector_score + 0.3 * ts_rank) AS combined_rank
  ```
- Expose an endpoint `POST /search/hybrid`.

**Testing:** Query a symbol name, verify it’s found even when semantic similarity is low.

**Achievement:** Improved retrieval accuracy, measurable later in evaluation.

## Phase 15: Agent tool system – search_code & read_file

**Concept:** Give the LLM two tools it can call: `search_code(query)` and `read_file(path, start, end)`. Build the function‑calling plumbing.

**Why:** This enables multi‑step reasoning, not just a single retrieval.

**Implementation:**
- Define tool schemas (JSON function descriptions).
- When the LLM returns a tool call, parse it, execute the tool (call our existing search/read APIs), and feed the result back into the LLM.
- We’ll use DeepSeek’s function calling (OpenAI‑compatible API).

**Tools:**
```python
tools = [
    {"type": "function", "function": {"name": "search_code", "parameters": {"query": "string"}}},
    {"type": "function", "function": {"name": "read_file", "parameters": {"file_path": "string", "start_line": "int", "end_line": "int"}}}
]
```

**Agent loop:**  
1. User question → LLM may decide to call `search_code("JWT generation")`.  
2. System executes it, returns results.  
3. LLM may then call `read_file("auth/service.py", 42, 68)`.  
4. LLM then composes final answer.

**Testing:** Mock tool results, assert the agent calls the expected tools.

**Achievement:** The assistant can now explore the codebase interactively.

## Phase 16: Agent loop with reasoning & multi‑step

**Concept:** Build a robust agent loop that handles up to N turns, summarises intermediate findings, and eventually synthesises a cited answer.

**Why:** Real‑world questions often need several lookups. The agent should not stop after one search.

**Implementation:**
- `run_agent(question, repo_id, max_turns=5)`
- On each turn, send the conversation so far and the list of tools.
- If the LLM returns a final message without a tool call, break.
- Otherwise, execute tools and append results as `tool` messages.
- Final answer is the last assistant message.

**Prompt engineering:** Instruct the agent to always cite file:line after each piece of evidence.

**Achievement:** The system becomes much more capable, able to answer complex “what will break if I change X?” style questions.

## Phase 18: Test discovery & Docker sandbox execution

**Concept:** Scan the repo for test files (e.g., `test_*.py`), and allow the agent to request test execution in an isolated Docker container.

**Why:** Running tests is the ultimate evidence for “why is this endpoint returning 500?” The agent can run the failing tests and inspect the output.

**Implementation:**
- Service that discovers test files and commands (e.g., `pytest`).
- `POST /repos/{id}/tests/run` – creates a `test_run` record.
- It starts a short‑lived Docker container (from a python image) mounting the repo, runs the specified test command, captures stdout/stderr.
- Store results in `test_results` table.

**Safety:** Only run commands from an allowed list; never allow arbitrary shell commands. Limit container resources and time.

**Testing:** Mock Docker API or use a test repo with a deliberately failing test.

**Achievement:** The system can execute real tests, bridging AI and actual engineering tools.

**Concept:** Add the tool `run_tests(test_path_or_marker)` to the agent’s toolkit. The agent can now, in one conversation, find relevant code, run tests, and explain failures.

**Why:** This is the “wow” feature – the AI diagnoses a 500 error by reading the code, running the related test, and seeing the stack trace, all without human intervention.

## Phase 20: Evaluation dataset & retrieval metrics

**Concept:** Create a set of question‑answer pairs for a test repository, with expected evidence files/lines. Use this to measure retrieval quality.

**Why:** Without evaluation, you’re guessing if changes improve the system. This gives you hard numbers.

**Implementation:**
- `eval_dataset` table: `question`, `expected_files` (JSON array), `expected_lines` (JSON).
- Script to run a question, record retrieved chunks, and compute `Recall@5`, `Precision@5`, `MRR`.
- Store results in `evaluation_runs`.

**Metrics calculations:**  
`Recall@k` = (# of expected chunks in top‑k) / total expected.  
`Precision@k` = (# of expected in top‑k) / k.

**Achievement:** You can now objectively compare retrieval strategies (e.g., semantic vs. hybrid).

## Phase 21: Answer quality & citation validation

**Concept:** Beyond retrieval, measure if the generated answer is correct and if the citations actually support the claims.

**Why:** Retrieval can be perfect, but the LLM might still hallucinate. You need to evaluate the final output.

**Methods:**
- **Citation precision:** For each citation in the answer, check if the cited lines contain the described logic. This can be automated with a simple text‑match or a second LLM call.
- **Answer correctness:** Use an LLM‑as‑judge (e.g., GPT‑3.5) to compare the generated answer to a reference answer, scoring from 1‑5.
- Store scores in `evaluation_runs`.

**Implementation:**  
- `evaluate_answer(question, answer, expected_answer)` script.
- `run_full_evaluation(repo_id)` that loops over dataset.

**Achievement:** You have a complete evaluation pipeline – a mark of a mature ML product.

## Phase 26: Scaling & performance optimisation

**Concept:** Optimise chunk retrieval with approximate indexing (pgvector’s `ivfflat` or `hnsw`), batch embedding generation, and caching frequent queries.

**Why:** If the repository is huge, vector search can slow down. We need to ensure sub‑second responses.

**Implementation:**
- Create an index: `CREATE INDEX ON code_chunks USING ivfflat (embedding vector_cosine_ops);`
- Use `hnsw` for better speed (pgvector 0.5+).
- Add Redis for caching LLM responses for identical queries.
- Profile and optimise database queries.

**Achievement:** The system stays fast even with 100k+ chunks.
